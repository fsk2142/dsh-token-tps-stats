## 1. 这是什么插件

在 DSH（一个 AI 编码助手的桌面客户端）输入框底部显示**当前会话的实时输出速度**（tok/s），
点击后弹出面板，左上角可以切换两个页签：

- **实时速度**：最近 1 / 3 / 5 分钟的折线图；
- **每步平均**：最近 5 / 10 / 20 步的表格（读取 / 输入 / 输出 / 命中 / 速度）。

数据来源是宿主提供的 `useChat` 快照：

- `legacy.partial = { turn, step, blocks }` —— **正在生成的这一步**，`blocks` 里的文本是
  **累计**的（宿主每来一帧就拼一次）；
- `legacy.nodes` —— 已完成的消息，带 `usage`（真实 token 账单）与 `timing`
  （`stepStartTime` / `firstTokenTime` / `completedTime`）。

插件自己按 100ms 一拍读快照、做差分，把新增字符按「两次采样的真实时间差」摊开
（`spread.ts`），再喂给速度计。

## 2. 用户报的现象

用户给了两张截图：

**实时速度页**（面板里显示 `当前 0 tok/s · 平均 0 · 峰值 0`，曲线是空的，
中间写着「这段时间还没有输出」）；同时**每步平均页**里，最近 5 步都有速度
（49 / 57 / 30 / 21 / 47 tok/s 之类）。

用户的问题原话：

> 假如一步很快结束了，是不是每步平均那里有速度，但是实时输出速度没有显示是不是因为太快了来不及

也就是说：**同一段时间，表格里每步都 20~60 tok/s，但实时的胶囊/曲线是 0 或很小**。

我还通过宿主事件日志（`session.v4.jsonl.zstd`，可解码成 11850 条事件）核对了真实数据：

```
时间跨度 296 秒、8439 帧、99020 字符（英文/代码）≈ 23576 token，长期平均 80 tok/s
```

## 3. 根因（三个，且互相叠加）

### 3.1 两处口径根本不同（这是设计，不是 bug）

| 位置 | 分母 |
| --- | --- |
| 「每步平均」的速度 | 输出 token ÷ 这一步**真正在生成**的时长（不含等工具） |
| 实时（胶囊与折线图） | 最近 **9 秒**的窗口平均，再走 3 秒一阶低通 |

分母差了一到两个量级。用户第一张截图里那几步（`#21.112` 生成 10.6s / 495 token），
表里读 47 tok/s；而它在实时口径下只占 10.6 秒里的一小段，被 9 秒窗口 + 3 秒低通
摊薄后——特别是**开流后的前 9 秒**——读数会低得多。

### 3.2 实时口径的分母**恒为 9 秒**，开流初期系统性偏低（这是真缺陷）

现行算法（`tps-meter.ts` 的 `windowedRate`）：

```
9 个 1 秒窗口，每个窗口算 (窗口内 token ÷ 1000ms)
把 9 个窗口的速率求和，再除以 9
空窗口按 0 计入（分母固定）
再走 3 秒一阶低通显示
```

后果：**刚开始流式的前 9 秒里，空格子全部按 0 进分母**。实测：

| 场景 | 真值 | 现行读数 |
| --- | --- | --- |
| 稳定 100 tok/s 持续 10 秒 | 100 | 峰值 **81** |
| 0.3 秒内吐 144 token（很短的一步） | 476 | 峰值 **4** |
| 一步开头 100ms 到 60 字符、随后稳定 | 32 | 峰值 6，0.9 秒才首次可见 |

用户看到的「实时 0 或很小」主要来自这一条。

### 3.3 60% 的步**根本没有可见正文**，实时口径下必然读 0（数据事实）

从 1824 条助手消息里统计：

```
有可见内容（正文 text 或思考 reasoning）：725 条（40%）
只有工具调用参数（tool-call，没有正文/思考）：1099 条（60%）
```

这 60% 的步在生成时，客户端快照里 `tool-call` 块的 `argsRaw` **在流式中途始终是空串**
（宿主只在 `block-end` 才填），所以插件拿不到任何可见字符 —— 实时读数只会是 0。

而这些步的生成时间并不短：

```
纯工具参数步共 1099 个，生成总时长 8299 秒
其中生成 >= 1 秒的 1099 个，>= 5 秒的 923 个
最长的几个：70s / 618 tok，39s / 213 tok，37s / 421 tok
```

也就是说：**模型有 8299 秒在「吐工具参数」，而实时胶囊在那段时间一律显示 0**。
用户自然觉得「实时没在工作」。

> 注：这一步的表里之所以有速度，是因为它用 `usage.outputTokens`（**包含**工具参数的
> token）÷ 生成时长 —— 表格是「事后结算」，实时是「当下观感」，两者没法靠调参对齐。

## 4. 已经做过的实测对比（这是给评审的重点）

### 4.1 数据

真实流式时间线：`8439 帧 / 296 秒 / 99020 字符 / 长期平均 80 tok/s`。

两个决定性事实：

- **82% 的帧 `dt = 0`**（宿主在同一毫秒连发好几帧），帧间隔中位数 **0ms**；
- 帧间隔 95 分位 287ms、99 分位 702ms、最大 1527ms。

### 4.2 测过的四种口径

外层都一样（9 个 1 秒桶 + 3 秒低通 + 800ms 空闲宽限 + 3 秒指数衰减回落），只换**目标值**：

| 代号 | 目标值算法 |
| --- | --- |
| **A** | 现状：9 个 1 秒窗口各自算速率，分母恒为 9 秒 |
| **B** | 自适应：本步已生成 token ÷ 本步已跨时长，**无下限** |
| **C** | 自适应 + **分母下限** `max(floorMs, 已跨时长)`，上限 9 秒 |
| **F** | 双窗口：前 1.5 秒用 2 秒短窗，之后线性过渡到 9 秒长窗 |
| **G** | 按**帧间隔**算瞬时速率 + 最近 8 帧中位数滤波 |

### 4.3 结果

真实流（真值 80）：

| 口径 | 峰值 | 开流 2~5 秒段均值 |
| --- | --- | --- |
| A 现状 | 92 | **28** |
| **B** | **1685** ❌ | — |
| C（下限 1.5s） | 92 | **74** |
| F 双窗口 | 92 | 74 |
| **G** | **2028** ❌ | 1500 |

合成场景「0.3 秒吐 144 token」（真值 476）：

| 口径 | 峰值 |
| --- | --- |
| A 现状 | **4** |
| C 下限 0.75s | 49 |
| C 下限 1s | 37 |
| C 下限 1.5s | 25 |
| C 下限 2s | 19 |

**B 与 G 直接排除**的理由相同：它们的分母会从 0 附近开始（B 是「已跨时长从 0 起」，
G 是「帧间隔常为 0」），而 82% 的帧 `dt=0` —— 直接除爆。

由此得到一个强约束：

> **唯一稳妥的观测量是「窗口内 token 总量 ÷ 窗口时长」**。
> 「换成瞬时速率」这条路在这份数据上不可行。

### 4.4 C 的下限怎么选（唯一旋钮）

真实流上，下限对峰值毫无影响（都是 94），只影响开流初期与短步的灵敏度：

| 下限 | 真实流峰值 | 短步峰值（真值 476） | 稳定 60 tok/s 的峰值 |
| --- | --- | --- | --- |
| 0.75s | 94 | 49 | 44 |
| 1s | 94 | 37 | 44 |
| 1.5s | 94 | 25 | 43 |
| 2s | 94 | 19 | 42 |
| 3s | 94 | 12 | 41 |

（60 tok/s 那列只有 41~44 是因为 3 秒低通还没爬完，与分母无关。）

## 5. 我的方案（尚未落地，等评审）

1. **把目标值的分母换成 `max(1500ms, 本步已跨时长)`，上限 9 秒**（= C，下限 1.5 秒）；
2. **长窗口 9 秒缩到 5 秒**（峰值不变、跟随更快）。

预期：短步 4 → 25，稳定 100 tok/s 81 → 96，真实流峰值 92 → 94（仍贴真值）。

**代价 / 风险**：

- 分母语义变了，`tps-meter` 里 3~4 条「分母固定 9」的单测要按新语义重写
  （只改期望值、不删用例）；
- `tps-history`（折线图）必须同步改，否则胶囊与曲线各说各话；
- 3.3 那条（60% 的步没有可见正文）**改分母解决不了** —— 那需要「拿到工具参数增量」，
  而宿主在流式中途不提供（`argsRaw` 恒为空串）。除非改成从别的事件源读，
  否则实时口径在这些步上只能是 0。

## 6. 想请评审回答的问题

1. **有没有比「窗口 token 总量 ÷ 窗口时长」更适合的观测量**？
   约束：只能看到字符增量（还大多是 ASCII/代码），token 数要等这一步结束才有；
   帧间隔 82% 为 0；不能用网络/持久化。
2. **C 的下限该取多少**？我们的取舍是「短步别太难看 vs 别虚高」，可以接受
   「短步读到 25 而真值 476」（因为那一步只有 0.3 秒，读者体感上也不需要精确值）。
3. **60% 的步显示 0 是否应该接受**？备选：显示「工具参数中」之类状态词 ——
   但用户之前明确否掉过状态词（他要那格只有 tok/s 语义）。有没有第三种做法？
4. 有没有我们没想到的口径 —— 例如「按字符到达的**包络**做平滑」、
   「用 3 秒内的 token 数 ÷ 3 秒，但对最近的桶加权」之类？请评估其在 `dt=0` 下的稳定性。
