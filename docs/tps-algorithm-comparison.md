# 实时速度口径：四种方案的实测对比

> 写于 2026-11-13。用户问「还有没有更好的计算方式反应实时速度」时做的对比研究。
> **本文只是研究记录，代码里仍是方案 A（现状）。**

## 为什么要做这次对比

用户观察到一个具体现象：

> 假如一步很快结束了，是不是每步平均那里有速度，但是实时输出速度没有显示

先确认了两边不是一套口径（这是设计，不是 bug）：

| 位置 | 算法 |
| --- | --- |
| 「每步平均」的速度 | 输出 token ÷ 这一步**真正在生成**的时长（不含等工具） |
| 胶囊（实时） | 最近 9 秒的平均，再走 3 秒低通 |
| 折线图 | 每秒一个点，每点也是 9 秒平均（与胶囊同口径） |

那么问题是：实时那套口径**本身还有没有优化空间**。

## 数据来源

`.tmp/replay.json` —— 本机真实流式时间线，**8439 帧 / 296 秒 / 99020 字符**
（字符全是英文与代码，按 `OTHER_CHARS_PER_TOKEN = 4.2` 换算 ≈ 23576 token，
长期平均 **80 tok/s**）。

两个关于这批数据的事实，它们决定了哪些算法可行：

- **82% 的帧 `dt = 0`**（同一毫秒连发好几帧），帧间隔中位数就是 0ms；
- 帧间隔 95 分位 287ms、99 分位 702ms、最大 1527ms —— 主线程被占住时会有长空档。

复现方法：`tests/client/replay-regression.test.ts`（没有该文件时整组自动跳过）。

## 测过的四种口径

全部用同一套「9 个 1 秒桶 + 3 秒低通 + 800ms 空闲宽限」的外层，只换**目标值**的算法：

| 代号 | 目标值算法 |
| --- | --- |
| **A** | 现状：9 个 1 秒窗口各自算速率，**分母恒为 9 秒**，空格子按 0 计入 |
| **B** | 自适应：本步已生成 token ÷ 本步已跨时长，**无下限** |
| **C** | 自适应 + **分母下限**（`max(floorMs, 已跨时长)`，上限 9 秒） |
| **F** | 双窗口：前 1.5 秒用 2 秒短窗，之后过渡到 9 秒长窗 |
| **G** | 按**帧间隔**算瞬时速率 + 中位数滤波（最近 8 帧） |

## 实测结果（真实数据 + 合成场景）

真实流（真值 80 tok/s）：

| 口径 | 峰值 | 2~5 秒段均值 | 首次可见 |
| --- | --- | --- | --- |
| A 现状 | 92 | **28** | 0.4s |
| **B 自适应（无下限）** | **1685** ❌ | — | 0.2s |
| C 自适应（下限 1.5s） | 92 | **74** | 0.2s |
| F 双窗口 | 92 | 74 | 0.2s |
| **G 帧率中位数** | **2028** ❌ | 1500 | 0.2s |

合成场景（短步：300ms 内 606 字符 ≈ 144 token，表里那行会读 476 tok/s）：

| 口径 | 峰值 |
| --- | --- |
| A 现状 | **4** |
| C 下限 0.75s | 49 |
| C 下限 1s | 37 |
| C 下限 1.5s | 25 |
| C 下限 2s | 19 |
| F 双窗口 | 25 |
| G 帧率中位数 | 83 |

**B 和 G 直接排除**：

- B 的分母从 0 起，第一帧就可能除出无穷大 —— 真实数据上峰值 1685；
- G 用帧间隔作分母 —— 82% 的帧 `dt=0`，同样除爆，真实数据上 2028。

这两条说明：**唯一的稳妥观测量是「窗口内的 token 总量 ÷ 窗口时长」**，
优化空间只在「窗口时长怎么取」，不在「换成瞬时速率」。

## 下限怎么选

C 的唯一个旋钮是分母下限。在真实数据上，下限对峰值毫无影响（全是 94），
只影响**开流初期与短步**的读数灵敏度：

| 下限 | 真实流峰值 | 短步峰值 | 稳定 60 tok/s 的峰值 |
| --- | --- | --- | --- |
| 0.75s | 94 | 49 | 44 |
| 1s | 94 | 37 | 44 |
| 1.5s | 94 | 25 | 43 |
| 2s | 94 | 19 | 42 |
| 3s | 94 | 12 | 41 |

（稳定 60 tok/s 那一列只有 41~44 是因为 3 秒低通还没爬完 —— 与分母无关。）

## 结论与建议

**A 的病根**：分母恒为 9 秒。开流后的前 9 秒里，空格子全按 0 进分母，
于是稳定 100 tok/s 只读出 81、0.3 秒的短步只读出 4 —— 系统性偏低，
而且偏得不是一点。

**建议改成**：

1. 目标值的分母换成 `max(1500, 本步已跨时长)`、上限 9 秒（= C，下限 1.5 秒）；
2. 长窗口 9 秒缩到 5 秒（峰值不变，跟随更快）。

改了之后：短步 4 → 25，稳定 100 tok/s 81 → 96，真实流峰值 92 → 94（仍贴真值）。

**代价**：这是破坏性改动 —— 「分母固定 9」的语义被改，`tps-meter` 里相关单测
（3~4 条）与 `tps-history` 的折线口径都要按新语义重写，**不能只改数字了事**。
折线图必须同步，否则胶囊与曲线会各说各话。

## 未采用的思路（留给后来者）

- **按帧间隔算瞬时速率**：真实数据里 82% 的帧 `dt=0`，必然除爆。除非先在
  `spread.ts` 之后做「到达节奏平滑」，但那是另一套口径，等于推翻现有的 9 秒窗。
- **双窗口混合**：实现复杂（多一套状态与混合权重），收益与 C 基本重合
  （真实流 92 vs 92，短步 25 vs 25），参数却多两个。
- **按 token 数而不是字符数算**：做不到 —— 流式 chunk 里只有字符，没有 token，
  真实 token 要等这一步结束才有（见 README「为什么是估算」）。
